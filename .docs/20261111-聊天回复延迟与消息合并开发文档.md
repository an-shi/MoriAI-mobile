# 聊天回复延迟与消息合并开发文档

> 文档日期：2026-11-11  
> 文档范围：用户发送消息后，角色何时开始回复，以及连续多条消息如何合并成一次交谈  
> 当前状态：已实现；两个延迟都可在「设置 > 聊天 > 回复延迟」调整

## 1. 背景

之前的逻辑是：用户发送一条消息后，立即调用模型生成回复。这样会出现三个问题：

- 用户刚发完第一句还在继续打字，角色就抢答；
- 用户隔两秒又补一条，角色把两条消息当成两轮独立对话；
- 连续发送文字、图片或表情包时，模型会收到多条分离请求，回复连续性很差。

现在改为“先等待、再合并、最后只请求一次”的回合逻辑。

## 2. 行为规则

### 2.1 情况 1：发出后结束输入

用户发出消息后没有继续输入：

- 等待 `发送后等待` 秒（默认 2 秒）；
- 期间没有新消息、也没有继续打字；
- 开始请求角色回复；
- 连续发送的多条消息会合并到同一轮。

### 2.2 情况 2：发出后还在输入

用户发出消息后继续输入：

- 取消“发送后等待”计时；
- 等待输入框失焦；
- 失焦后再等待 `失焦后等待` 秒（默认 1 秒）；
- 然后请求回复。

### 2.3 情况 3：停顿后又继续输入

用户发出第一句后停顿了一两秒，又开始打字：

- 如果“发送后等待”计时还没到，会取消计时，进入情况 2；
- 如果已经触发回复，则当前回复继续进行，新消息进入下一轮排队。

## 3. 消息合并

### 3.1 同一轮

从第一条到“开始请求前”的所有用户消息视为一轮：

- 文字、图片、表情包都算；
- 同一轮只发起一次模型请求；
- 只有当轮开始时的消息快照进入本轮上下文，轮开始后再发的消息不会提前影响当前回复。

### 3.2 多轮

如果用户在角色回复期间又发了消息：

- 新消息进入排队；
- 当前回复完成后，不会立即连续请求，而是重新走延迟和失焦规则；
- 新消息同样可以合并成下一轮。

### 3.3 历史快照

`roundHistoryForBatch()` 保证：

- 本轮批次内的所有用户消息都进入上下文；
- 批次之后仍在排队的用户消息被排除；
- 助理回复按顺序追加。

## 4. 状态机

文件：`lib/services/chat_reply_scheduler.dart`

`ChatReplyScheduler` 负责：

| 方法 | 作用 |
|---|---|
| `scheduleAfterSend()` | 用户发送后开始等待；连续发送会重置计时 |
| `noteInputActivity()` | 用户在发送后继续输入，取消发送计时，改为等待失焦 |
| `noteFocusChanged(bool)` | 焦点离开时启动失焦计时；焦点回来时取消失焦计时 |
| `markStarted()` | 回复真正开始，取消所有等待 |
| `cancel()` / `dispose()` | 清空、停止或离开页面时取消等待 |

规则：

- 发送后没有输入：只等发送延迟；
- 发送后输入过：必须等失焦延迟；
- 连续发送会重置对应计时；
- 回复期间发消息不启动计时，等当前回复结束后再统一调度。

## 5. 设置

数据模型：`lib/models/chat_reply_settings.dart`  
存储：`lib/services/chat_reply_settings_store.dart`

| 字段 | 默认值 | 说明 |
|---|---|---|
| `sendDelaySeconds` | `2` | 用户发完消息没有继续输入时，等待多久再回复 |
| `focusLeaveDelaySeconds` | `1` | 用户发送后继续输入过时，输入框失焦后再等待多久 |

入口：「设置 > 聊天 > 回复延迟」

- 「发送后等待（秒）」：0-30；
- 「失焦后等待（秒）」：0-30；
- 输入完成后立即保存；
- 持久化 Key：`chat_reply_settings_v1`。

## 6. 与队列的关系

原有 `ChatQueueStore` 继续保存未回复的用户消息 ID：

- 消息发送后先写入队列并持久化；
- 开始回复时取队首整批作为一轮；
- 回复完成后从队列移除这一批；
- 如果队里还有新消息，重新走延迟调度；
- 应用重启后，未完成队列会恢复并立即处理，不再等待输入焦点。

## 7. 已知限制

- 延迟基于客户端定时器，应用退到后台或被杀后不保证继续计时；
- 如果用户发送后一直保持输入框焦点并继续输入，角色会一直等待失焦；
- 应用重启恢复队列时会立即处理，不再等待失焦；
- 延迟值按整数秒配置，不支持 1.5 秒这类小数；
- 合并只影响“回复轮次”，聊天记录里仍然保留每条消息；
- 群聊同样使用这套延迟和合并逻辑，本轮发言者只收到一轮请求。
